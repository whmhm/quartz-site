# 流式接口数据格式化：断连重连与 Markdown/MathJax 冲突处理

本文整理流式接口前端处理的两个典型问题：**SSE 断连后的断点重连**，以及**流式 Markdown 中公式与 Markdown 语法的格式化冲突**。原文中重复、乱码与技术偏差之处已在文末"审查与修正说明"中统一标注。

## 一、流式接口断连重连（SSE 场景）

### （一）核心思路

SSE（Server-Sent Events）基于 HTTP 长连接，断连后需要重新创建 `EventSource` 实例。断点重连的核心是两件事：

1. **精准标记断连位置**：每条消息携带可排序的断点标识（如 `chunkId`、消息 `id` 或序列号），客户端持久化最近一次已处理的断点；
2. **安全恢复数据传输**：重连时携带断点向服务端请求增量数据，并对断点有效性进行校验，失败时降级为全量请求。

### （二）关键机制

#### 1. 连接状态监听

通过 `EventSource.readyState` 判断连接状态：

| readyState | 常量 | 含义 |
| --- | --- | --- |
| 0 | `EventSource.CONNECTING` | 连接建立中（含重连） |
| 1 | `EventSource.OPEN` | 连接已建立，可接收事件 |
| 2 | `EventSource.CLOSED` | 连接已关闭，不再重连 |

> 补充：浏览器原生 `EventSource` 在断连时会自动重连，若服务端事件携带 `id:` 字段，重连请求会自动带上 `Last-Event-ID` 请求头。需要自定义退避策略或业务断点参数时，才需在 `onerror` 中手动关闭并重建实例。

#### 2. 重连防抖与退避

避免断连后频繁发起重连，采用**指数退避**并限制最大间隔（如 1s → 2s → 4s，上限 30s）；连接恢复后重置重试计数。

#### 3. 断点有效性校验

若断连时间过长，超过服务端数据缓存时效，重连时服务端可能返回"断点无效"。此时必须清空本地断点标记，重新发起全量请求：

```js
sessionStorage.removeItem('lastChunkId')
```

#### 4. 页面卸载清理

在 `beforeunload` 事件中关闭连接并清除断点标记，避免下次打开页面时复用过期断点：

```js
eventSource.close()
sessionStorage.removeItem('lastChunkId')
```

### （三）参考实现

```js
/**
 * 创建带断点续传与指数退避的 SSE 连接
 * @param {string} url 接口地址
 * @param {object} handlers
 * @param {(data: string) => void} handlers.onMessage 业务消息回调
 * @param {(data: string) => string} handlers.extractId 从消息中提取断点 ID
 */
function createResumableSSE(url, { onMessage, extractId }) {
  let eventSource = null
  let retryTimer = null
  let retryCount = 0
  let manualClosed = false

  const connect = () => {
    const lastId = sessionStorage.getItem('lastChunkId')
    const fullUrl = lastId
      ? `${url}?lastChunkId=${encodeURIComponent(lastId)}`
      : url

    eventSource = new EventSource(fullUrl)

    eventSource.onmessage = (event) => {
      // 连接恢复，重置退避计数
      retryCount = 0

      // 断点无效：清空标记，降级为全量请求
      const data = JSON.parse(event.data)
      if (data.code === 'INVALID_CURSOR') {
        sessionStorage.removeItem('lastChunkId')
        eventSource.close()
        connect()
        return
      }

      onMessage?.(event.data)
      sessionStorage.setItem('lastChunkId', extractId(event.data))
    }

    eventSource.onerror = () => {
      eventSource.close()
      if (manualClosed) return
      // 指数退避：1s、2s、4s……上限 30s
      const delay = Math.min(1000 * 2 ** retryCount++, 30000)
      retryTimer = setTimeout(connect, delay)
    }
  }

  const close = () => {
    manualClosed = true
    clearTimeout(retryTimer)
    eventSource?.close()
    sessionStorage.removeItem('lastChunkId')
  }

  window.addEventListener('beforeunload', close)
  connect()

  return { close }
}
```

## 二、Markdown 与 MathJax 的格式化冲突

### （一）冲突根因与符号清单

公式中常用的 `#`、`*`、反引号等符号同时是 Markdown 语法符号，Markdown 解析器会先于 MathJax 执行，导致公式被误解析。需要先筛选冲突符号，**仅对公式区域内的冲突符号做转义**，普通文本保持原样。

| 原始符号 | 转义后 | 冲突的 Markdown 语法 | 说明 |
| --- | --- | --- | --- |
| `#` | `\#` | 标题 | LaTeX 中 `#` 为宏参数符/注释语境 |
| `*` | `\*` | 斜体 / 粗体 | 公式中表示乘法 |
| `` ` `` | `` \` `` | 行内代码 | 需避免被识别为代码区起始 |
| `[` | `\[` | 链接起始 | 注意 TeX 语义风险，见审查说明第 2 条 |
| `]` | `\]` | 链接结束 | 同上 |
| `|` | `\|` | 表格分隔 | 公式中可能表示集合或范数 |
| `_` | `\_` | 斜体 / 粗体 | 公式中下划线使用频率高 |

转义保留规则：已经带反斜杠的符号（如 `\$`）不重复转义，仅处理未转义的原始符号。

### （二）公式符号预转义

#### 1. 实现原则

- 先用公式边界标记（`$$...$$` 或 `$...$`）锁定公式区域，只对区域内内容执行转义；
- 用字符替换映射批量处理，保证操作可重复、可回退；
- **优先使用"区域匹配 + 区域内替换"的写法，不要依赖变长后行断言**（兼容性问题见审查说明第 4 条）。

#### 2. 推荐实现

```js
// 公式区域内的冲突符号（已转义的不重复处理）
const CONFLICT_RE = /(^|[^\\])([#*|[\]`_])/g

function escapeMathConflicts(text) {
  // 先锁定公式区域，仅在区域内执行转义
  return text.replace(/\$\$[\s\S]*?\$\$|\$[^$\n]+\$/g, (formula) =>
    formula.replace(CONFLICT_RE, '$1\\$2'),
  )
}
```

原文给出的正则 `/(?<=\$\$[\s\S]*)(#|\*||[)(?=[\s\S]*$$)/g` 存在字符类残缺、定界符未转义等问题，已由上述实现替代。

### （三）转义后的处理链路

转义后的公式需经过 **Markdown 格式化 → MathJax 渲染** 两个阶段：

1. **Markdown 格式化阶段**：冲突符号已带转义，Markdown 解析器（如 marked）将其视为普通文本，不会触发标题、斜体、代码等语法，公式结构得以完整保留；
2. **MathJax 渲染阶段**：公式进入 MathJax 排版。这里要特别注意——**MathJax 不会自动剥离任意反斜杠**，预转义字符如何还原必须显式处理（详见审查说明第 1 条）。

MathJax 基础配置参考：

```js
window.MathJax = {
  tex: {
    // 常规做法：行内公式用单 $，行间公式用双 $$，两者不要使用同一组定界符
    inlineMath: [['$', '$']],
    displayMath: [['$$', '$$']],
    // 仅用于让公式外的 \$ 按字面美元符处理，并非"移除公式内所有反斜杠"
    processEscapes: true,
  },
  startup: {
    typeset: true,
  },
}
```

如果坚持采用预转义方案，稳妥做法是在 Markdown 解析完成后、MathJax 排版前，**自行对公式区域做一次定向去转义**，而不是依赖 MathJax 配置：

```js
function unescapeMathConflicts(html) {
  return html.replace(/\$\$[\s\S]*?\$\$|\$[^$\n]+\$/g, (formula) =>
    formula.replace(/\\([#*|[\]`_])/g, '$1'),
  )
}
```

### （四）特殊场景处理

#### 1. 公式内包含代码符号

若公式中出现反引号（如 `` $$ 代码示例: x = 1 ` $$ `` 形式的片段），需在预转义阶段统一处理反引号，避免 Markdown 将其识别为行内代码；去转义阶段再原样还原。

#### 2. 流式分段传输的公式

公式可能被拆到多个 chunk（如第一段 `$$E = mc^2`，第二段 `\# 注释$$`）。处理原则：

- 维护缓冲区，检测到未闭合的公式定界符（`$$` 数量为奇数）时，**尾部残片留在缓冲区，不进入 Markdown 解析**；
- 缓冲时保留已转义符号，待公式合并完整后再统一执行转义和格式化，避免分段重复添加反斜杠。

#### 3. 转义有效性校验

在 Markdown 格式化后、MathJax 渲染前，检测公式区域内是否仍存在未转义的冲突符号，遗漏则补全：

```js
function findUnescapedConflicts(text) {
  const issues = []
  for (const formula of text.match(/\$\$[\s\S]*?\$\$|\$[^$\n]+\$/g) ?? []) {
    // 用"非反斜杠前缀"捕获，避免后行断言的兼容性问题
    const bad = formula.match(/(^|[^\\])([#*|[\]`_])/g)
    if (bad) issues.push({ formula, bad })
  }
  return issues
}
```

### （五）方案优势与注意事项

**优势**

- 从源头阻断冲突：在 Markdown 解析前处理公式符号，无需调整解析器执行顺序；
- 适配现有流程：不改动 Markdown / MathJax 核心逻辑，改造成本低。

**注意事项**

- 避免过度转义：只处理公式区域内的冲突符号，普通文本中的 `#`、`*` 等保持原样；
- 去转义必须显式：不要指望 MathJax 配置自动还原反斜杠，推荐使用第三章的占位保护方案或自定义去转义函数；
- 流式场景先缓冲后处理：未闭合的公式、代码围栏一律只缓存不改写，防止半截标记被正则破坏。

## 三、审查与修正说明

以下是对原始材料的技术审查结论，按严重程度排列。

### 1. `processEscapes: true` 的作用描述有误（重要）

原文称开启该配置后 MathJax 会"自动移除公式内的 `\` 转义"。实际上，MathJax v3 中 `processEscapes` 的唯一作用是让**公式外部**的 `\$` 按字面美元符号处理，**不会**剥离公式内的 `\#`、`\^`、`\*` 等反斜杠。预转义字符的还原必须自行实现（见上文 `unescapeMathConflicts`），或改用占位保护方案。

### 2. 部分符号的 TeX 转义语义与预期不同（重要）

- `\[`、`\]` 在 LaTeX 中本身是**行间公式定界符**，把公式里的方括号转义成 `\[` `\]` 再交给 MathJax 可能直接报错；
- `\^` 是 TeX 的**抑音符号命令**（需要参数），`\^2` 渲染结果不是上标；上标应保持 `^2`；
- `\*` 是 TeX 的断行乘号命令，并非字面 `*`；
- 可安全转义且能渲染回原字符的主要是 `\#`、`\$`、`\%`、`\&`、`\_`、`\{`、`\}` 这一组。

因此"统一加反斜杠再让 MathJax 自动还原"的方案对 `[ ] ^ * ` 反引号等符号并不成立，这也是更推荐占位保护方案的原因。

### 3. 公式定界符配置不当

原文将 `inlineMath` 与 `displayMath` 都配置为 `['$$', '$$']`，行内与行间无法区分。常规配置应为行内 `$...$`、行间 `$$...$$`。

### 4. 正则在旧环境不兼容且原文正则本身有残缺

- 原文正则 `/(?<=\$\$[\s\S]*)(#|\*||[)(?=[\s\S]*$$)/g` 存在字符类残缺（`||[`）、定界符 `$` 未转义、反引号丢失等问题，无法运行；
- 变长后行断言（`(?<=...)` 中用量词）在 Safari 16.4 之前的 JavaScriptCore 中不支持。本文改为"先匹配公式区域、再在区域内替换"的两段式写法，避开后行断言；校验正则也改用 `(^|[^\\])` 捕获前缀实现同等判断。

### 5. 更稳妥的工程替代方案：公式占位保护

预转义方案本质是在公式文本上"做加法再做减法"，链路长且 TeX 语义陷阱多。主流 Markdown 数学插件（remark-math、markdown-it 的 math 插件）采用的是**占位保护**思路，流式场景同样适用：

```js
// 1. Markdown 解析前，提取公式并替换为不含任何冲突符号的占位符
const mathStore = []
const protectedText = text.replace(
  /\$\$[\s\S]*?\$\$|\$[^$\n]+\$/g,
  (match) => {
    mathStore.push(match)
    return `@@MATH_${mathStore.length - 1}@@`
  },
)

// 2. 占位符对 Markdown 完全透明，安全执行格式化
const html = marked.parse(protectedText)

// 3. 渲染前原样还原公式，交给 MathJax 排版，全程不改动公式内部字符
const finalHtml = html.replace(
  /@@MATH_(\d+)@@/g,
  (_, i) => mathStore[Number(i)],
)
```

该方案与代码区保护、流式分片缓冲可以共用同一套"提取 → 占位 → 解析 → 还原"机制，公式内部字符零改写，不存在转义过度或 TeX 语义偏差问题。

### 6. 其他修正

- 原文在 SSE 段落出现 `ws.close()`，这是 **WebSocket** 的关闭方法，SSE 对应方法为 `eventSource.close()`，已修正；
- 原文"Markdown 与 MathJax 冲突"部分大段重复（预转义规则、正则、配置出现两遍），已合并去重；
- 原文转义符号表格被压成纯文本且 `[` 的转义结果丢失，已重建为标准 Markdown 表格；
- 补充了原生 `EventSource` 自动重连与 `Last-Event-ID` 请求头机制的说明，避免重复造轮子。
